## 一、先修三个问题，否则新增指标也可能误导你

### 1. 现在自定义 `grounding_loss` 的日志分母有问题

在 `trainer.py` 中，`compute_loss()` 每个 microbatch 都累加 `grounding_loss`；但 `log()` 输出时，只除以 `gradient_accumulation_steps`，没有除以这个日志窗口实际积累的 microbatch 数。你的 A7/A8 脚本又是每 20 个 optimizer step 才输出一次日志。

举个例子：

```text
每个 microbatch 的真实 grounding loss = 2
gradient_accumulation_steps = 4
logging_steps = 20

窗口内累计：20 × 4 × 2 = 160
现在的日志：160 ÷ 4 = 40
正确的 microbatch 平均值：2
```

**我抽取原代码的方法运行，复现了这个结果。**

它会带来两个问题：自定义 component loss 的绝对值不对；窗口在结束、额外日志调用或恢复训练时变短，数值尺度还可能发生变化。

但要注意：**这是这条自定义日志的错误，不代表实际 backward 的 loss 在这里被放大了 20 倍，也不代表你看到的所有跳变都是假的。**

应该修成“实际累计总和／实际计数”，并明确统计的是 microbatch 均值还是有效样本均值。不能简单再硬除以一个 `logging_steps`，因为窗口不一定完整。

### 2. 某些样本没参与 grounding，却以零损失进入了平均

你的 `_compute_grounding_loss()` 遇到没有视觉 token、没有有效标签、标签长度严重不匹配等情况，会加入一个零损失；最后对整个 batch 取均值。

因此：

```text
两个有效样本，损失分别为 10、10 → batch loss = 10
一个有效样本损失为 10，另一个被跳过 → batch loss = 5
```

**模型没有变好，loss 却下降了一半。**

反过来，如果某一段有效样本比例恢复了，loss 又可能上跳。只看 loss，你分不清是“模型突然变差”，还是“这一步终于有更多样本真正提供监督”。

所以必须同时记录：

$$
\text{有效 grounding 比例}
\quad+\quad
\text{仅有效样本的平均 grounding loss}.
$$

这次先记录，不顺手修改实际训练损失的分母，避免把“监控改造”和“训练算法变化”混在一起。

### 3. 训练和异步评估的 W&B 写入路径需要统一

现在已有 HF 默认 W&B callback，另外自定义 callback 又直接调用 `wandb.log()`；异步 `eval_daemon` 还会恢复训练 run，按旧 checkpoint 的 step 写评估结果。

这里需要区分：

> **W&B 内部记录序号，不等于 optimizer step，也不等于被评估 checkpoint 的 step。**

W&B 不支持任意回填已经过去的 history step；自定义横轴才适合表达训练步数和 checkpoint 步数。比如训练已经到 1000，checkpoint-400 的评估才完成，就不应该直接向内部 `step=400` 写入。([Weights & Biases][1])

我的建议很简单：**训练只保留一个 writer；异步评估使用单独、关联到训练的 eval run，以 checkpoint step 为横轴。**不需要新建监控服务。

## 二、对你的 ZwerGe，每层最有必要的是这五类指标

你现在的主要计算链路是：

$$
\text{中间层表示}
\rightarrow W_q,W_k
\rightarrow \text{空间 logits}
\rightarrow p_l
\rightarrow \text{KL loss}.
$$

代码已经计算了逐层 KL 和 logits，只是前者被累加后没有单独传出，后者在上层调用中被丢掉。因此，**补这部分不需要再跑一次 backbone**。

我建议每个参与训练的 probe 只记录下面五类。表中的键是示意名称，完整命名与 HF 前缀处理在说明里。

| 指标                          | 它回答什么问题        | 你应该怎样理解                         |
| --------------------------- | -------------- | ------------------------------- |
| `L18/kl_mean`               | 哪一层先出问题？       | 总 loss 上升时，是所有层都升，还是某一层先升？      |
| `L18/logit_rms_centered`    | 输出打分尺度是否失控？    | logits 突然变大，softmax 可能突然变得极尖    |
| `L18/entropy_norm`          | 分布变得更集中还是更分散？  | 接近 1 更均匀，接近 0 更尖锐；尖锐不等于正确       |
| `L18/gt_floor_mass`         | 正确目标是否落入概率截断区？ | 检查当前 `clamp(1e-8)` 是否正在削弱重要监督项  |
| `L18/grad_rms_postclip_max` | 这个读出器的梯度是否异常？  | 与全局裁剪前 norm 配合，区分局部异常、整体过大与梯度消失 |

这些是**五种指标乘以你的 probe 层数**，不是给整个 backbone 的每个模块安装监控。要定位到具体层，这部分分辨率值得保留。

### 为什么要记录 logits，而不只看概率？

假设某次更新前后，空间打分从：

```text
[0.2, 0.1, 0.0, ...]
```

变成：

```text
[20, 10, 0, ...]
```

排序可能没有变，但分布的尖锐程度、损失和梯度状态可能变化很大。

因此，用去均值后的尺度：

$$
s_l=\sqrt{\frac1N\sum_j(z_{l,j}-\bar z_l)^2}
$$

观察 logits。减掉均值是因为 softmax 不受所有 logits 同时加一个常数影响。

**这对即将做的 SVD 初始化尤其重要：你需要知道它究竟提供了更好的初始方向，还是只是让第一步的输出尺度变大了。**

### 为什么 entropy 要归一化？

不同截图的视觉 token 数不一样。均匀分布的熵是 \(\log N\)，所以直接比较原始 entropy，会混入截图大小的影响。

建议每条样本先计算：

$$
H_{\mathrm{norm}}(p)=\frac{H(p)}{\log N},
$$

再做样本平均。不要先把不同样本的概率分布混起来再算熵。

### `gt_floor_mass` 是针对你这份代码特别有价值的一项

你现在的损失使用：

```python
torch.log(p.clamp(min=1e-8))
```

而不是直接从 logits 得到 log-probability。

我建议记录：

$$
\boxed{
m_{\mathrm{floor}}
=
\sum_j y_j\,\mathbf 1[p_j<10^{-8}]
}
$$

它不是“有多少背景 patch 的概率很小”，而是：

> **有多少目标分布的质量，落在模型几乎不给概率、又被 clamp 截断的地方。**

这一区别很重要。背景概率小通常没什么；正确目标的概率被压得极低，才值得关注。

我做的单目标小测试中，过尖且预测错误的 logits 可以出现“loss 有限，但这个损失的梯度已经为零”。真实 Gaussian 标签更复杂，不能据此断言整个模型梯度都会消失，但这个指标能帮助识别这种状态。

**本轮只记录它，不顺手改 loss。**之后真发现它经常触发，再单独验证数值实现的修复。

## 三、全局层面，只补能解释原因的几组量

### 数据：记录“实际学了多少”和“这一批本来是什么样”

除了有效比例、有效样本 loss，我建议再保留两个数据量：

**一是 repair/fallback 比例。**你的数据路径会随机换样本重试、对轻微标签长度差异插值，以及在 Gaussian 权重过小时退回 binary label。这些都是代码中真实存在的分支。

正常曲线只画一个比例，具体原因、样本 ID 放异常记录，不要给每种错误都铺一整页面板。

**二是均匀预测的参考 KL：**

$$
L_{\mathrm{uniform}}
=
\log N_{\mathrm{vis}}-H(y).
$$

这个量由当前视觉位置数和标签分布决定。即使模型预测保持均匀，换一批 \(N\) 更大、目标更集中的样本，KL 也会变化。

因此，当真实 loss 和这个参考值一起上升时，先检查数据组成；不要马上认定参数更新出了问题。

### 优化器：保留全局裁剪前峰值，补上新 token 的梯度

全局只需要重点看：

$$
\text{裁剪前 gradient norm 峰值},\quad
\text{裁剪发生比例},\quad
\text{实际 LR}.
$$

另外，**你的新 special-token embeddings 可能是可训练的**，会改变送入多个 probe 的共享输入。它不是普通 frozen-backbone 参数，所以应该单独有一条梯度记录，不能只监控 `W_q/W_k`。这部分参数在训练入口被单独创建，优化器也有独立参数组。

一个常见实现陷阱是：到 `on_log` 再查 `.grad`，梯度可能已经被清空了。另一个是把 `on_pre_optimizer_step` 得到的梯度叫作“裁剪前梯度”——已核对的 HF callback 顺序中，这个回调位于裁剪之后。([Hugging Face][2])

所以说明里明确要求：

> **在实际优化器边界采集，准确标明 preclip/postclip；只观察，不重复裁剪、不重复 unscale。**

### A8：补损失拆分，保留已有融合统计

A8 再增加：

$$
L_{\mathrm{fuse}},\quad L_{\mathrm{aux}},\quad \tau,
$$

并修正已有 layer weights、omega entropy 的聚合口径。

这样才能区分：

> 各个 probe 仍然正常，但融合器突然开始选错层。

注意你代码中的 \(\tau\) 是**乘在 cosine score 上**，不是除数；分析时别把方向解释反了。A7 的 omega 是固定均匀值，不应该拿它讨论“融合塌缩”。

## 四、真正能让你少重跑的，是异常发生时留下“样本＋局部上下文”

**只有曲线，没有样本身份，很多问题仍然查不出来。**

尤其你的 dataset 会在失败后随机换样本。只记录“sampler 请求了第 123 条”，不代表模型真的训练了第 123 条。现在返回给 Trainer 的数据里，也没有足够的稳定身份信息。

我建议做一个很小的滚动记录：

正常时只保留最近几个更新窗口的标量；遇到 loss 脉冲、非有限值或数据修复，保存对应事件。里面包含：

```text
optimizer step / microbatch / global rank
原本请求的样本 ID / 实际训练的样本 ID
原图定位、bbox、处理后尺寸
视觉 token 数、标签长度、标签是否修复
anchor 来源与位置
每层 KL、logits 尺度、entropy、目标 floor mass
异常层输入与 Q/K 的 RMS 摘要
当前 LR 与梯度摘要
```

**不保存完整激活，不保存全量梯度，不自动上传截图。**

输入激活与 Q/K 的摘要只用于事件定位，不必都画成常规曲线。这样，发生异常后能回答：

> 是送进 L24 probe 的表示已经异常，还是表示正常、经过 `W_q/W_k` 后打分尺度才突然变大？

记录位置也只在 probe 边界，不需要监控整个 backbone。

同时要保留 NaN/Inf 的独立计数，因为 HF 的 `logging_nan_inf_filter` 可以过滤 loss 的显示，但**不等于阻止了这些值影响梯度计算**。([Hugging Face][3])

这能显著缩小排查范围，但不能保证任何故障都无需复现。合理目标是：**需要时只重放已经定位的少量样本，而不是重新训练整场实验。**

## 五、上传仍然可以每 20 步一次，但不能只在第 20 步观察

这是这次改造最重要的操作原则：

$$
\boxed{\text{采集频率}\neq\text{上传频率}}
$$

我建议保留当前每 20 个 optimizer step 上传一次的节奏；窗口内部持续累计均值、最大值、计数，并保留异常事件。

例如，20 次观测中：

```text
19 次 loss = 1
1 次 loss = 41
```

只上传均值，你看到的是 3；同时上传窗口最大值，你才能知道曾经出现过 41。

没必要把 `logging_steps` 简单改成 1，更没必要每层每次 forward 都直接调用 W&B。

另外加一个**固定的 32 条开发集诊断**：step 0，以及每 100 步左右运行一次。只做直接读出，不生成 AR 坐标、不走 native fallback、不画 PNG。记录各层 KL 和实际解码后的点是否进入 bbox。

它回答的是：

> 当前训练 loss 的变化，是因为刚好换了一批难数据，还是模型在同一组输入上真的变差了？

这组数据必须来自独立开发集，不拿正式测试集反复调参。32 条也只能作动态诊断，不能承担完整泛化结论。

## 六、以后你可以怎样读这些曲线？

先记住下面四种典型组合就够了。它们是排查顺序，不是自动判定根因的规则。

| 看到的组合                                            | 优先考虑什么                             |
| ------------------------------------------------ | ---------------------------------- |
| 总 loss 下降，有效样本 loss 不变，有效比例下降                    | 无效样本的零损失稀释了均值，不是模型学好了              |
| 某层 KL 上升，logits 尺度变大，entropy 下降，目标 floor mass 增加 | 这个读出器可能变得过尖且自信地预测错误；检查该层 Q/K 与前一更新 |
| 训练 loss 偶发升高，数据参考 KL 或 repair 比例一起变，固定开发集稳定      | 先查 batch 组成、标签与数据处理，不急着归咎于优化器      |
| 各层 KL 稳定，只有融合 loss 变差，omega 集中到少数层               | 优先检查 A8 融合，而不是重训所有 probe           |

还有一点：**当前 forward 的坏结果会产生当前梯度，当前更新主要影响后续 forward。**同一步 loss 和 gradient norm 同时升高，并不能直接证明“梯度升高导致了这一刻的 loss 升高”。因此异常记录必须对齐更新前后，而不只是共享一个模糊的 step 数字。
